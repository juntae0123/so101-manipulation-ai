## 1. 계측기 방어를 코드로 만들었다

계측기 결함이 6건 누적된 뒤, 사용자가 "미리 발생할 버그를 생각하고 미리 지침에
박아라" 고 했다. 사후 발굴을 그만두라는 뜻이다.

**`AI/tools/lint_instruments.py`** (8,077 B) — 알려진 안티패턴 8종을 커밋 전에 잡는다.

```
grep-c-in-and-chain · zero-or-more-number · compare-without-empty-check
no-set-u · grep-case-sensitive-status · bare-except-pass
minmax-without-guard · float-equality
```

만든 날 **저장소 116개 파일에 돌려 오탐 4건을 걷어냈다.**
`nan-propagating-reduce` 규칙은 추가했다가 **제거**했다 — `max(1, int(seconds*rate))`
를 잡아서 오탐 4건이 났다. **오탐이 많은 계측기도 고장난 계측기다.**

**`AI/docs/RULE_instrument_authoring.md`** — 린터가 못 잡는 것 ⑪개 + 체크리스트 + 사례표.
오늘 ⑩(가용성≠기능)과 ⑪(검색 0건 전 범위 확인)을 추가했고, 사례 7·8 을 올렸다.
**8번은 어시스턴트가 오늘 낸 것이다.**

## 2. 재현성 — cuDNN 이 원인으로 확정 🟢

`torch.manual_seed` 만으로는 CUDA RNG 도 cuDNN 알고리즘 선택도 안 덮인다.
가설이 아니라 재봤다:

```
기본 모드         val 3.01492 / 2.99024   → 다르다
--deterministic   val 2.71397 / 2.71397   → 같다
```

`train_bc.py` 에 `torch.cuda.manual_seed_all` · `random.seed` 를 추가하고
`deterministic` 을 EXP_LOG `conditions` 에 넣었다. **조건을 바꿨으면 조건에 적는다**(규칙 ⑥).

⚠️ 이 계측기 자체가 처음엔 고장나 있었다. `grep -o 'val [0-9.]*'` 의 `*` 가
"0개 이상" 이라 학습 시작 전 안내문의 `val ` 이 숫자 없이 매칭됐고,
**빈 값끼리 비교해 "같다" 를 출력했다.** 계측기 결함 6번.

## 3. 서버 이식 — `is_available()` 이 거짓말을 한다 🟢

V100 에서 학습이 `CUDA error: no kernel image is available` 로 죽었다.

```
torch 2.11.0+cu128   is_available() True · CC (7,0) · 그런데 sm_75 이상 빌드
torch 2.13.0+cu126   get_arch_list() = ['sm_50','sm_60','sm_70','sm_75','sm_80','sm_86','sm_90']
                     실연산 [1.0, 1.0, 1.0, 1.0] 통과
```

두 검사(`is_available`, `get_device_capability`)를 다 통과하고 첫 학습에서 죽는다.
**가용성 확인은 기능 확인이 아니다.** 규칙 ⑩ 으로 박았다.
상세 `TS_v100_cuda_arch_0916.md`.

⚠️ 강제 재설치가 `numpy 2.2.6 → 2.5.2` 도 같이 올렸다. opencv/numba/zarr 와의
충돌 여부 **미확인**. 학습은 돌았으므로 치명적이진 않다.

## 6. 계측 — 일정의 전제를 숫자로

```
1 epoch (100편 · batch 8 · 1,686 스텝)     156 초
롤아웃 1편 (기동 포함)                      31.44 초
롤아웃 한계원가 ((t5−t1)/4)                 24.6 초
2400편 ÷ GPU 5장                           3.3 시간
```

→ PREREG 6절의 축소 조건(1편 60초 초과)은 **발동하지 않는다.** n=300 그대로 간다.

⚠️ 24.6초는 **최악값**이다. 계측에 쓴 5편이 전부 실패해서 12초 풀타임아웃을 돌았다.
성공하면 조기 종료하므로 실제 캠페인은 더 빠르다.

`EPOCHS = 60` 확정. 156초 × 60 = 2시간 36분 < 3시간 예산. 산술로는 69까지 되지만
156초에 기동시간이 포함된 **상한**이고 3잡이 같은 zarr 를 워커 12개로 읽으면
IO 경합이 있어 내렸다. **결과 보고 안 바꾼다.**

## 7. 고친 것 2개 (둘 다 "조용히 넘어가는" 결함)

**`patch_lift_threshold.py`** — `lift_height 0.13` 은 IK 명령 목표인데 성공 판정은
`expert.py` 2곳 · `evaluate.py` 1곳에 **0.1 로 하드코딩**돼 있었다.
같은 개념으로 읽으면 같은 체크포인트가 2/100 과 100/100 으로 갈린다.
전문가 자신의 리프트가 **0.1193 ± 0.0001 m** 🟢 라 0.13 은 전문가도 못 넘는다.
레거시 체크포인트는 `success_min_lift_source: legacy_default` 로 **기록**한다.

**`patch_train_seed.py`** — `umi_adapter/train.py` 에 `--seed` 가 없어서
3회 반복이 "3시드"가 아니라 "비결정성 3회"였다. `training.seed=N` 을 **`+` 없이**
넣어 키가 없으면 즉시 죽게 했다. 1 epoch 실행으로 키 실재 확인 🟢.

⚠️ **이 패치의 첫 판이 멱등이 아니었다.** `old` 가 `new` 안에 포함되는 치환이라
"이미 적용됨" 검사가 통과해버려, 2회차에 `--seed` 가 두 번 등록되는 코드를 만들었다.
사본에 2회 돌려서 잡았고, 표식(marker) 기반 검사 + 중복 검산으로 고쳤다.
**패치 도구도 계측기다.**

## 9. 2번째 타겟이 두 번 무너졌다 — 오늘 가장 중요한 발견

상세 `MEASURE_task2_envelope_0916.md` · `TS_task2_selection_0916.md`

| 후보 | 결과 | 원인 |
|---|---|---|
| `box_top` 상면·박스 | **0/60** | 수직 구속 IK 도달 z 가 0.02~0.04 뿐. 전문가는 0.130 필요 |
| `box_side` 측면·박스 | **0/60** | 박스 중심 높이 25mm 로 수평 진입 불가 |
| `can_left` 측면·캔·좌측 | **20/20** | 채택 |

**`run_side_expert` 는 물체 위치는 따라가지만 크기·높이는 못 따라간다.**
잡는 높이 = 물체 중심(하드코딩), 대기 지점 = 50mm 뒤(고정).
박스에서 물체 이동량이 **정확히 0.0000**, 양측접촉 False, normal_force 0.34 N —
그리퍼가 닿지도 못했다.

→ 제품의 **5스킬 물체를 고를 때마다 전문가 코드를 새로 써야 한다.**
→ 타겟 도메인(D-AI-19 다품종 소량생산 **소형부품**)은 대체로 낮다.
   **이 시뮬 자산으로 그 도메인을 시연할 수 없다.** HW·PM 확인 필요.

D-AI-49 확정: T1 `can_side`(E1 체크포인트 재사용) / T2 `can_left` (y [0.06, 0.10]).
T2 데이터 100편 완료 — 시드 6300–6403, 104시도로 100편(전문가 약 96%) 🟢.

⚠️ **한계를 먼저 말한다** — T1/T2 는 "다른 조작 태스크 2종" 이 아니라
**"같은 태스크의 다른 위치 2개"** 다. 가장 가까운 가장자리가 25mm 밖에 안 떨어져
있어 G3b(교차평가)가 **안 떨어질 수도 있다.** 그 경우 결론은 "정책이 구분을 못 했다"
가 아니라 **"두 타겟을 충분히 다르게 잡지 못했다"** 다. 미리 적어둔다.
