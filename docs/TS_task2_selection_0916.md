# TS — 2번째 타겟 태스크가 두 번 0/60 으로 무너진 과정

2026-09-16 · 김준태(트랙 B) · handoff 패키지 · MuJoCo 3.13.0 · SO-101

**"고쳤다" 가 아니라 "어떻게 좁혔나" 를 적는다.**
결과 수치는 `MEASURE_task2_envelope_0916.md`, 결정은 `DECISIONS_AI_0916_task2.md`.

## 시작 — 검증 안 된 가정 하나

과제 ③ 에 2번째 타겟이 필요했다. 접근 축이 직교하면 교차평가 차별력이 가장 크므로
**상면 파지(top-down)** 를 골랐다.

`simulation/env.py` 의 기본값(workspace_x [0.23,0.29], home_q, open_width 0.08 …)을
그대로 config 로 옮겼다. 근거는 **"기본값이니 돌 것"** 이었다.

⚠️ 그 가정은 검증된 적이 없다. handoff 패키지는 `can_side` 로만 검증돼 있고,
**top-down 경로가 이 패키지에서 성공한 기록을 나는 본 적이 없었다.**

20편 요청 → **0/60.**

## 1라운드 — 0 을 받고 무엇을 했나

0 은 세 가지를 동시에 뜻할 수 있다.

```
(a) 태스크가 어렵다
(b) 내 config 가 틀렸다
(c) 계측기가 고장났다
```

**0 이라는 숫자만으로는 못 가른다.** 그래서 `generation_report.json` 의
실패 사유를 분해했다.

```
60건 전부  Unreachable target [..., 0.12999521]: IK residual 0.0667~0.0690
```

균일한 residual = 아슬아슬한 게 아니라 **구조적으로 밖**이다. (a)/(b) 로 좁혔다.

⚠️ 여기서 내가 **실패 지점을 lift 목표라고 말했다. 틀렸다.**
`pre = 물체중심 − 0.01 + 0.115` = 0.025 − 0.01 + 0.115 = **0.12999521** 로
정확히 맞는다. **pre-grasp 에서 죽었고 lift 까지 가지도 못했다.** 즉시 정정했다.

## 2라운드 — 추측으로 x 를 조정하지 않았다

여기서 "x 를 줄여서 다시 20편" 이 제일 빠른 유혹이다.
그러면 틀릴 때마다 60편을 다시 돌린다.

**포락선을 한 번에 훑었다.** `rotation=None`(수직 구속) IK 를 격자로 풀었다.

```
x 0.10~0.36 (27) × z 0.02~0.20 (19) = 513칸
도달 28칸 = 5.5%
도달 가능 z = 0.02 ~ 0.04 m
```

전문가가 필요로 하는 z 는 pre 0.130 · lift 0.155.
**config 로 고칠 수 있는 범위가 아니다.** `home_q` 도 소용없다 —
`env.ik` 는 내부 고정 시드 5개로 풀기 때문에 시작 자세와 무관하다.

→ (b) 기각. (a) 확정. **상면 파지 폐기.**

## 3라운드 — 같은 실수를 반복하지 않으려고 먼저 쟀다

측면 파지는 되는 게 확인돼 있으니 **물체를 바꾸는** 쪽으로 돌렸다.
이번엔 config 를 쓰기 전에 물체 형상과 측면 포락선을 먼저 읽었다.

```
box : BOX  36 × 36 × 50 mm · 35 g   안착 z 0.0250
can : CYL  ⌀67.8 × 101.8 mm · 349 g  안착 z 0.0509

측면 포락선  z=0.027 → x 0.37~0.46 · z=0.051 → x 0.34~0.46
```

캔이 쓰는 `workspace_x [0.385, 0.415]` 가 박스 도달권 안에도 들어간다.
그대로 두고 20편 → **또 0/60.**

## 4라운드 — 이번 0 은 갈래가 둘이었다

```
35건  pre-grasp IK 실패   목표 x 0.348~0.362 (포락선 하한 0.37 미만)
25건  도달 후 파지 실패   lift_m 정확히 0.0000 · 양측접촉 False · 0.34 N
```

첫 번째는 예측대로였다. `pre = grasp − approach×0.05` 라 물체가 0.40 이면
pre 가 0.363 으로 밀려난다. 작업영역을 올리면 고쳐진다.

**두 번째가 결정적이다.** 물체 이동량이 **정확히 0** 이다.
팔은 갔는데 그리퍼가 박스에 닿지도 않았다.

원인: 전문가는 **물체 중심 높이로 수평 진입**한다(하드코딩).
캔은 중심이 50.9mm 라 여유가 있지만 **박스는 25mm** 다.
그 높이로 수평 진입하면 그리퍼가 테이블에 걸린다.
`close_width` 를 어떻게 바꿔도 **안 닿는 건 못 고친다.**

→ **박스 측면 파지 폐기.** 30분 타임박스 소진 — 착수 전에 정해둔 값이다.

## 5라운드 — 대역을 재고 골랐다

같은 캔·같은 측면 파지로 **작업영역 y 만** 옮기는 쪽으로 재정의했다.
`approach = obj[:2] − [0.04, 0]` 정규화라 y 가 커지면 접근 방향이 회전한다.

첫 시도 `y [0.10, 0.16]` → 20/32 = **62.5%.** 게이트 80% 미달.
여기서도 좁혀보고 다시 돌리는 대신 **한 번에 훑었다.**

```
y      성공/시도 (n=5, 시드 9000~9004)
0.000    5/5     ← 계측기 검증행
0.020~0.080  5/5
0.100    4/5
0.120    3/5
0.140    1/5
0.160    1/5
0.180    3/5   ← 비단조. 설명 못 함. 안 쓴다
```

**y=0.000 의 5/5 가 계측기 검증이다.** `can_side` 본 설정이 100편 100% 였으므로
여기서 5/5 가 안 나오면 이 스윕을 믿을 수 없다. 통과했다.

`y [0.06, 0.10]` 채택 → 20편 요청 → **20/20 = 100%.** 낭비된 시도 0.
이후 100편 본수집도 104시도 100편(약 96%).

⚠️ **작업영역 조정은 1회로 미리 제한했고 그 안에서 끝났다.**
80% 나올 때까지 계속 줄이는 건 태스크 설계가 아니라 게이트 맞추기다.

## 배운 것

**1. 0 을 받으면 사유를 분해하기 전에는 아무 결론도 못 낸다.**
"태스크가 어렵다 / 설정이 틀렸다 / 계측기가 고장났다" 가 같은 0 으로 나온다.

**2. 추측 조정 대신 포락선을 훑는 게 싸다.**
20편 재시도 ≈ 2분, 격자 513칸 ≈ 1분. 두 번 이상 조정할 것 같으면 훑는 게 이긴다.

**3. 스윕에는 정답을 아는 행을 넣는다.**
y=0.000 이 그 역할을 했다. 그게 없으면 스윕 결과 자체를 검증할 방법이 없다.

**4. 이 패키지의 조작 능력은 한 가지뿐이다.**
높이 10cm급 물체의 측면 파지. 그 밖은 전문가 코드를 새로 써야 한다.
**5스킬 물체 선정에 직결되고, 타겟 도메인(소형부품)과 부딪친다.**
