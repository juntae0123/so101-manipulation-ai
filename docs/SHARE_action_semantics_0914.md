## 핵심 표 🟢

조건당 **독립 학습 3회 × 롤아웃 n=100 = 300 시행**

| | `action = state[t+1]` (계약 0.3.0) | `command = ctrl` |
|---|---:|---:|
| 성공률 | **0/300 = 0.0%** | **22/300 = 7.3%** |
| 95% 구간 | [0.0, 1.3%] | [4.9, 10.9%] |
| 시드별 | 0 / 0 / 0 | 13 / 1 / 8 |
| **닫는 순간** | **158.1 / 158.4 / 158.3mm** | **45.2 / 42.5 / 48.8mm** |
| 평균 상승 | 0.00cm | 0.41~0.66cm |

**성공률 신뢰구간이 겹치지 않습니다.** 그리고 더 강한 증거는 닫는 순간 거리입니다 —
**3.5배 차이에 두 분포가 전혀 겹치지 않습니다.**

⚠️ 158mm 는 **다섯 개 조건에서 재현**됐습니다 (물체 지터 0/±25/±50mm, 편수 59~60,
시드 0·1·2). 데이터가 무엇이든 폭 0.4mm 입니다.
**계약 규약 아래서는 정책이 무엇을 학습하든 같은 자리에서 닫습니다.**

⚠️ **7.3% 는 게이트 20% 한참 미달입니다.** 원인 하나를 제거한 것이지 푼 것이 아닙니다.
그리고 시드 편차가 큽니다(1~13%) — **"13%" 단독 인용은 하지 말아 주십시오.**

## 1. 무엇을 관측했나 🟢

계약 0.3.0 규약(`cam_wrist` 1대 · `action[t]=state[t+1]`)으로 시뮬 60편씩 3조건 수집,
각 학습 3회 × 롤아웃 n=100.

```
조건 j0 (물체 고정)      val 0.052 / 0.045 / 0.053   롤아웃 0.0% / 0.0% / 0.0%
조건 j25 (±25mm)        val 0.099 / 0.096 / 0.080   롤아웃 0.0% / 0.0% / 0.0%

bc          0/100 =  0.0%   평균 상승 0.00cm
scripted   84/100 = 84.0%   평균 상승 4.31cm
hold/zero   0/100            (정상)
[closing_moment] 닫는 순간 158.1mm
```

**씬은 멀쩡합니다** — scripted 84%, ceiling·task_validity 게이트 전부 통과.
망가진 것은 학습 정책뿐입니다.

**닫는 순간 158mm 가 결정적입니다.** 기존 BC v3 는 15.7~23.6mm 였습니다.
7배입니다. 팔이 물체 쪽으로 가지도 않고 제자리에서 그리퍼만 닫습니다.

⚠️ 그리고 **val loss 는 오히려 아주 낮습니다.** 표준화 단위로 0.05,
실수집 UMI(0.34)보다 7배 정확합니다. 손실만 보면 최고 성적입니다.

## 2. 메커니즘 🟢 (4·5절에서 검증됨)

```
action = state[t+1]              타깃이 "이미 간 거리"
   ↓
그 거리는 관측 없이 87~94% 예측된다   (0914 측정 🟢)
   ↓
모델이 0.05 SD 로 거의 완벽히 맞힌다
   ↓
롤아웃에서 자기 예측을 다시 먹는다 = "가던 대로"
   ↓
정지에서 시작하면 정지가 고정점. 팔이 안 움직인다
```

`data.ctrl`(내린 명령)은 다릅니다. **제어기가 쫓아가는 목표라 현재 자세보다 앞서 있고,
`ctrl − qpos` 에 "어디로 가려는가"가 담깁니다.** 그것이 움직임을 만듭니다.

`state[t+1] − state[t]` 는 **이미 도달한 거리**이고, 30Hz 에서 그 값은 아주 작습니다
(실데이터 0.001~0.002, 계약 단위).

## 4. 계기는 제 변경입니다

오늘 `data/collect.py` 를 계약 0.3.0 에 맞추려고 이렇게 고쳤습니다.

```
전  action = normalize(data.ctrl[:6])     내린 명령
후  action = state[t+1]                    실제 도달한 다음 상태
```

계약 `validate()` 가 `action[:-1] == state[1:]` 을 강제하므로 **수집기가 따르려면
이렇게 할 수밖에 없었습니다.** 즉 문제는 제 패치가 아니라 **규약 자체**일 수 있습니다.

그리고 이 변경으로 **`data.ctrl` 이 버려집니다.** 계약에 그 필드가 없습니다.

## 6. 트랙 A 에 무엇을 요청드리나

**① 확인 부탁** — 실수집 UMI 변환에서 `action` 을 어떻게 만드시는지.
계약 검증기를 통과했으니 `state[t+1]` 일 텐데, **원본 UMI raw 에 "명령/목표" 에 해당하는
값이 따로 있는지**가 핵심입니다. EEF 목표 pose 같은 것이 남아 있다면 그것이
`ctrl` 에 해당하고, 살릴 수 있습니다.

**② 되돌릴 조건 검토 (D-AI-46)** 🟡 — 제 제안은 **계약을 되돌리지 않고 필드를 추가**하는 것입니다.

```
action    계약 그대로 state[t+1] 유지   (검증기·기존 데이터 호환)
command   신설. 내린 명령 / 목표 pose.  학습은 이쪽을 쓴다
```

`action` 을 바꾸면 수집분이 전부 무효가 되지만, 필드 추가는 기존 데이터를 안 깹니다.
다만 **기존 수집분에는 `command` 가 비어 있어** 재수집 또는 역산이 필요합니다.

⚠️ **계약 변경이므로 양 트랙 합의와 D- 기록이 필요합니다. 제가 단독으로 정하지 않습니다.**

**③ 그 전까지** — 실데이터로 학습한 체크포인트의 롤아웃 수치를 아무 데도 인용하지 마시기 바랍니다.
지금 상태로는 0% 가 나올 가능성이 높고, 그것이 데이터 품질 문제로 오독될 수 있습니다.
