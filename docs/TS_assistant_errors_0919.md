## 1. 스윕 잡에 `MUJOCO_GL=egl` 이 없어 5개 GPU 잡이 전부 즉사

### 증상
```
mujoco.FatalError: an OpenGL platform library has not been loaded into this process
GLFWError: b'X11: The DISPLAY environment variable is missing'
→ 5개 잡 전부 exit 1 (첫 조건 렌더 시점)
```

### 어떻게 좁혔나
`set -eu` 라 첫 실패에서 죽는다. 그래서 exit 가 **즉시** 났고, 20편 중간이 아니라
**첫 관측 렌더**에서 죽었다는 것이 시간만으로 좁혀졌다. 로그 마지막 프레임이
`env.py:114 mujoco.Renderer(...)` 였다.

### 진짜 원인 — 내가 대조를 절반만 했다
지침에 *"일괄 실행 스크립트의 명령은 전부 `--help` 또는 소스로 인자를 대조한 뒤 쓴다"*
가 있다. 나는 `evaluate.py` 의 **argparse 를 소스로 대조했고**, 그걸 근거로
"인자 대조 🟢" 이라고 문서와 docstring에 적었다. **환경변수는 안 봤다.**

저장소의 기존 러너 8종이 전부 이 줄을 갖고 있었다 —
`run_e1_train.sh:61` · `run_e2.sh:22` · `run_e2_folds.sh:82` ·
`run_dagger_campaign.sh:19` · `run_chunking_campaign.sh:19` · `check_reproducibility.sh:22` …
**한 번만 grep 했으면 나왔다.**

### 왜 자체검증이 못 잡았나
자체검증 11행이 전부 **기하와 조건표**만 봤다. 잡 파일의 내용을 한 줄도 검사하지
않았다. 생성물을 안 보는 계측기였다.

### 조치
- `JOB_HEADER` 로 `export MUJOCO_GL=egl` + `cd` + 사전 확인을 묶었다
- 자체검증 3행 추가 (11 → 14): 헤더에 그 줄이 있는가 · 빼면 걸리는가 · cd 하는가
- 생성된 잡 파일에 `bash -n` 구문 검사까지 돌려 확인 🟢

### 일반화
**인자 대조 ≠ 실행 환경 대조.** 다음부터 러너를 새로 쓸 때는
`grep -rn "export \|^[A-Z_]*=" 기존_러너` 로 **환경변수를 먼저 훔쳐본다.**
기존에 돌던 스크립트가 있으면 그게 사양이다.

## 2. 배치 solver 초판이 720 IK 전부 0 — 앵커를 내가 새로 만들었다

### 증상
```
기준선(시뮬 홈 정렬)  0 / 10편
1단 최고              0 / 10편   (후보 72 × 10편 = 720 IK)
2단 상위 5개          전부 편 0/10 · 웨이포인트 0/90
```

### 하마터면
"어디에 놔도 안 되니 자세(orientation) 문제다" 로 결론낼 뻔했다.
**그럴 수 없다 — 양성 대조가 없었다.** 720번 다 0 인 것과 IK 호출이 틀린 것이
같은 출력이다. 이 프로젝트에서 9번 반복된 바로 그 모양이다.

### 진짜 원인
초판은 **시연 자체의 파지 자세를 유지한 채 위치와 월드 z yaw 만** 흔들었다.
v10 은 `robot_base_alignment_applied: false` 다 — 시연 자세는 **로봇 좌표계에
놓인 적이 없다.** z 둘레 회전만으로 정렬될 리가 없다.

그리고 이건 **이미 답이 있던 문제**다.
`MEASURE_real_grasp_ik_0917` §2 원문:
```
grasp  T_base[t] = T_grasp_sim @ inv(chain[closure]) @ chain[t]
       → waypoint 533/535 = 99.6%
```
나는 그 문서를 읽고(오늘 브리핑에 99.6% 를 인용까지 했다) **다른 앵커를 새로 만들었다.**
자세를 자유 변수로 둔 것 자체가 틀렸다 — 전문가 식에서 **물체 위치가 접근 방향을,
접근 방향이 자세를 정한다.** 자세는 고를 수 있는 값이 아니다.

### 조치
- 앵커를 0917 과 **같은 식**으로 되돌렸다
- 자유 변수를 **물체를 놓는 (x, y) 하나**로 줄였다. z 는 물체가 정한다
- **양성 대조를 넣었다** — 시드 0 의 실제 물체 위치로 먼저 재고,
  거기서 0 이 나오면 `exit` 한다. 결론을 안 낸다
- 자체검증 8 → 11. 판별 행 4개 (물체 옮기면 자세도 바뀌나 · inv 빼면 틀리나 ·
  접근점과 같은 위치면 죽나 · 앵커식이 닫힘 pose 를 정확히 T_grasp_sim 으로 보내나)

### 일반화
**새 앵커·새 좌표 규약을 만들기 전에 MEASURE 를 먼저 grep 한다.**
이미 통과한 규약이 있으면 그게 사양이다. 오늘 나는 같은 문서를 인용하면서
동시에 그 문서의 결론과 다른 것을 짰다.

**그리고 0 만 나오는 스윕에는 반드시 양성 대조를 같이 돌린다.**
"전부 실패" 와 "계측기 고장" 을 가르는 것은 그 행 하나뿐이다.

## 3. 🔴 `check_real_traj_ik.py` 관절한계 검사가 무력화돼 있었다 — 0917 수치 재검 필요

### 증상
`solve_grasp_anchor` 양성 대조에서 **90/90 전부 `joint_limit` 거부.**
양성 대조 가드가 막아서 결론을 안 냈다 (그 가드가 없었으면 "어디에 놔도 안 된다"로 갔다).

### 원인 — 같은 이름을 두 뜻으로 썼다
```python
lo, hi = env.limits[:, 0], env.limits[:, 1]   # 관절 한계 (rad, 5개)
...
lo, hi = span if span else (0, chain.shape[0] - 1)   # ← 구간 인덱스로 덮어씀
...
if np.any(q < lo - 1e-6) or np.any(q > hi + 1e-6):   # 관절각 vs 정수 인덱스
```
관절각은 rad 라 거의 항상 구간 인덱스보다 작다 → **전부 joint_limit.**
`span=None` 일 때도 `lo=0` 이라 **음수 관절각이 전부 거부**된다.

### 이미 발견됐던 결함이다 — 수정이 저장소에 안 들어왔다
`MEASURE_real_grasp_ik_0917.md` §7 결함 **#11**:
> *"거부 404/404 이 전부 `joint_limit` / 구간 인덱스 `lo,hi` 가 관절 한계 변수를 덮어씀"*

그런데 그 문서를 추가한 커밋(`5c541d4`)의 파일과 **오늘 파일의 md5 가 같다**
(`03e85b4b…`). 즉 **경보만 넣고 수정은 안 들어왔다.** 문서에도
*"경보를 넣어 자동화했다"* 라고만 적혀 있다.

### 그래서 지금 불확실해진 것 🟡
```
29.2%   (앵커 start · 구간 full)   span=None → lo=0 → 음수 관절각 전부 거부.
                                  이 코드로 나온 값이면 **과소평가**다
533/535 (앵커 grasp · 구간 grasp)  이 코드였다면 0/535 여야 하는데 99.6% 다.
                                  **앞뒤가 안 맞는다** — 다른 코드로 돌렸거나
                                  서버에서 손으로 고쳐 돌렸고 그게 커밋 안 됐거나
```
**둘 다 재실행 전까지 인용하지 않는다.** 533/535 는 오늘 브리핑·PDF·도경 회신에
이미 인용했다. 재실행 결과가 나오면 정정한다.

### 조치
- `q_lo, q_hi` 로 이름 분리 (2026-09-19)
- 자체검증에 **소스 검사 행** 추가 — `check_episode` 본문에
  `lo, hi = env.limits` 와 `lo, hi = span` 이 같이 있으면 **수치를 내지 않고 죽는다**.
  값 검사로는 못 잡는 종류라 소스를 직접 본다

### 일반화
**한 함수 안에서 같은 이름을 두 뜻으로 쓰지 않는다.** 문법 검사도 타입 검사도
못 잡고, 값도 그럴듯하게 나온다. 0917 에 발견해놓고 고치지 않은 것이 더 큰 문제다 —
**"발견"과 "수정"을 같은 칸에 적지 않는다.**

## 4. 🔴 jaw 게이트의 판정 규칙이 뒤집혀 있었다 — 이중 보정을 낼 뻔했다

### 서버 실측 (2026-09-19) 🟢
```
site_owner_body    gripper_tcp
jaw_axis_in_tcp    [1.0, -3.9e-17, 2.1e-16]     → TCP +X 와 0.000도
tcp_z_in_world     [1, 0, 0]   접근축이 월드 +X
tcp_x_in_world     [0, 1, 0]   턱이 월드 +Y 로 열린다
```

### 초판 규칙이 낸 답 — 틀렸다
초판: *"TCP +X 와 0도 → 레거시 프레임 → 92.789도를 넣어라."*
**그 매핑에 근거가 없었다.** 92.79도는 `grasp_so101_ver1.yaml` 이 **gripper body
로컬 프레임**에서 잰 값이고, 내가 재는 것은 **TCP site 프레임**이다. 다른 프레임이다.

목표 자세 `sim_grasp_pose` 의 회전은
`column_stack([cross([0,0,1], ap), [0,0,1], ap])` — **x축이 접근축에 수직인 수평,
곧 턱 방향**이다. 모델 TCP 의 x축도 턱 방향이다. **같은 뜻의 축이므로 추가 회전 0도.**

황도경 회신과 일치한다. 초판 규칙대로였으면 **정확히 이중 보정**이 됐다 —
막으라고 받은 지적이 만들어낼 사고를 내 게이트가 낼 뻔했다.

### 조치
상수 매핑을 없앴다. 이제 **턱 축이 TCP 의 어느 축과 정렬됐는지만** 본다.
x축이면 보정 0, 아니면 **보정값을 지어내지 않고 죽는다.**
실제 자세 오차는 `solve_waypoints` 의 측지각 검사가 웨이포인트마다 따로 잡는다.
자체검증 판별 행 2개 (92.79 넣으면 거부 · 축 어긋나면 죽는다).

### 일반화
**프레임을 안 적은 각도는 각도가 아니다.** 92.79도가 어느 프레임 기준인지
문서에 있었는데 내가 다른 프레임에서 재고 같은 수로 취급했다.
